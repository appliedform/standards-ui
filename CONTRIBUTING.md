# Contributing to Standards UI

This repository implements the Standards React contract and the public Instrument
pack. Component fixes, reproducible design failures, accessibility findings and
package-consumer improvements are useful contributions. A code fix is not required
to report a problem.

Changes to authored design rules, the schema, compiler or MCP server belong in the
[Standards foundation repository](https://github.com/appliedform/standards/blob/main/CONTRIBUTING.md).
This guide covers the React target; it does not replace that repository's contribution
process or introduce a new agreement here.

## Set up and check

Use Node.js 20, the version used in [CI](.github/workflows/ci.yml), and npm. From the
repository root:

```sh
npm ci
npm run check
```

`check` verifies generated metadata, compares vendored contracts with public upstream
`main`, builds both packages, audits the contract/materials, and runs the regression
tests. Initial dependency installation and the upstream freshness check need network
access. No private repository or token is required for Instrument.

After dependencies are installed, these focused checks work offline:

```sh
npm run generate:check
npm run build
npm run audit
npm test
```

The tests inspect built output, so rebuild after changing source. The package test
creates actual tarballs and installs a temporary consumer using local dependency
fixtures; it checks imports, contracts, CSS paths and strict TypeScript types without
registry access. If freshness cannot run, report that limit rather than describing
the full check as passing.

## Know which files to edit

| Files | Role and change rule |
|---|---|
| `packages/core/src/index.ts` | Authored shared types, `defineMove` and the hand-written `JOBS` taxonomy; the audit checks taxonomy against pack contracts |
| `packages/instrument/src/moves/`, `Root.tsx`, `Band.tsx`, `primitives.tsx` | Authored React implementation; fix rendering and behaviour here |
| `packages/instrument/src/index.ts` | Authored public exports; retain `.js` extensions so generated declarations support NodeNext |
| `packages/instrument/src/styles/tokens.css` | Runtime stylesheet; keep design values aligned with Instrument's canonical token source |
| `packages/instrument/tokens.json`, `archetypes.json` | Vendored contracts generated by the foundation compiler; do not redefine them here |
| `packages/instrument/src/meta.ts` | Generated locally from the vendored archetype contract with `npm run generate`; never edit by hand |
| `packages/*/dist/` | Generated declarations, bundles and copied CSS; rebuild locally, do not commit hand edits or build output |
| `tests/`, `scripts/`, package manifests and documentation | Authored support for implementation and distribution |

An implementation failure against the existing contract belongs here. A proposed
change to Instrument's rules, token meanings, moves or the shared job taxonomy needs
an upstream design/contract change first. Do not change a contract merely to make a
failing component pass. Explain any public prop, export or dependency change and its
effect on existing consumers.

For a vendored update:

1. Link the upstream change and identify its commit. Instrument's authoring inputs
   are [SOURCE.md](https://github.com/appliedform/standards/blob/main/packs/instrument/SOURCE.md)
   and [assets/tokens.css](https://github.com/appliedform/standards/blob/main/packs/instrument/assets/tokens.css).
   Follow the foundation's compilation checks there.
2. Copy the resulting `tokens.json` and `archetypes.json` into the Instrument package.
   Update the runtime stylesheet and components only where the accepted change requires it.
3. Run `npm run generate` and include changed vendored files and generated `meta.ts`
   in the PR. Describe which component behaviours are affected.
4. Run `npm run check`. Freshness compares against upstream `main`; a coordinated
   change awaiting upstream merge must state that dependency and resolve it before
   claiming the full check passes. Do not disable freshness to conceal the mismatch.

## Fixtures and evidence

For a behaviour fix, add a small synthetic fixture that reproduces the failure and
a valid control case. Test the public built output or package boundary rather than
merely repeating the implementation. Existing examples cover
[signed Series geometry](tests/series.test.mjs),
[Plate percentage validity and emphasis](tests/plate.test.mjs), and
[fresh package consumption](tests/package.test.mjs).

Choose edge cases relevant to the change: empty and dense content, long labels,
zero and signed data, non-finite inputs, or invalid dimensions. Preserve the supplied
facts and labels. A numerical guard must not quietly turn invalid evidence into a
valid-looking measurement.

For layout or visual changes, also provide before/after render evidence with the
same fixture, viewport and fonts. Include a narrow and wide viewport where relevant
(for example 390px and 1280px), the browser and zoom, and any scroll or clipping
behaviour. Load the token CSS and use `InstrumentRoot`; identify whether the intended
fonts or fallbacks were available. Include the fixture or reproduction steps so the
screenshot can be checked independently.

Record applicable keyboard/focus checks, accessible names and structure, contrast,
non-colour cues and whether information remains available to assistive technology.
Static charts still need understandable textual values and labels. A source audit,
React-element assertion or successful screenshot does not establish full accessibility,
responsive behaviour or design quality. State what you inspected and what remains
untested; describe a static prototype as such.

## Report a component failure as a designer

Open a [UI issue](https://github.com/appliedform/standards-ui/issues/new) with:

- The component, package version or commit, and the task the design should serve.
- The smallest safe set of props/data or a short description that reproduces the issue.
- The expected behaviour or applicable Instrument rule, and the observed failure.
- A screenshot or recording when useful, plus viewport, browser, fonts and reproduction steps.
- Whether the issue concerns meaning, composition, legibility, accessibility or implementation.

For agent-generated work, include only the relevant sanitised brief and steps needed
to reproduce the failure. Do not post an entire private conversation. An annotated
screenshot and a clear explanation are useful even if you cannot write React or a test.
Report security vulnerabilities through [SECURITY.md](SECURITY.md) instead of a public issue.

## Privacy and licensing

Use synthetic or explicitly reusable fixtures. Remove client identifiers, personal
data, credentials, private instructions and proprietary design-pack content from
code, logs, screenshots and PR descriptions. Identify the source and licence of any
third-party material; include only work you are entitled to contribute. Do not add
font binaries or other assets without checking their distribution rights.

Implementation code is covered by [MIT](LICENSE). Instrument's design-system material
is covered by [CC BY 4.0](packages/instrument/LICENSE-INSTRUMENT); the
[package notice](packages/instrument/NOTICE) explains the boundary and attribution.
Preserve applicable notices and identify adaptations. Public React contributions
do not require access to the proprietary catalogue.

Keep a PR focused on one behaviour or clearly related change. Explain the trigger,
result, validation and remaining limits using the
[UI PR template](.github/pull_request_template.md).
